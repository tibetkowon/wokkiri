# ECC 작업 절차

새 대화에서는 `HANDOFF.md`로 현재 상태를 확인하고, 사용자의 요청과 `docs/product-spec.md`의 확정 규칙을 기준으로 완료 조건을 정합니다. 요청을 받은 채팅이 아래 표에서 해당하는 ECC 스킬을 선택하고 그 지침을 읽습니다.

## 요청별 스킬 선택

| 요청 | 적용할 절차 |
|---|---|
| 코드의 현재 동작을 묻는 질문 | 관련 코드와 테스트를 찾아 근거를 답합니다. 조사 작업자에게 추가 문맥이 필요하면 `ecc:iterative-retrieval`로 읽을 범위를 좁힙니다. |
| 새 기능 추가 | `ecc:orch-add-feature`의 계획 단계에서 아래 설계 협의를 진행하고, 확정된 완료 조건을 구현자에게 전달합니다. |
| 기존 기능의 규칙 변경 | `ecc:orch-change-feature`로 호출부·화면·테스트에서 어떤 기대값이 달라지는지 확인합니다. |
| 기존 동작의 오류 수정 | `ecc:orch-fix-defect`로 오류를 재현하는 테스트를 먼저 만들고 수정 후 같은 테스트를 다시 실행합니다. |
| 동작을 유지하는 코드 정리 | `ecc:orch-refine-code`로 변경 전후의 동작을 확인합니다. |
| 여러 모듈이나 기존 데이터에 걸친 변경 | 구현 전에 `ecc:change-impact`로 영향을 받는 경로를 찾고 실제 diff와 대조합니다. |
| 인증·권한·민감한 입력 처리 | 검증자가 `ecc:security-review`로 접근 허용·거부와 데이터 노출 여부를 확인합니다. |
| 모바일 화면 변경 | `ecc:browser-qa`로 임시 DB의 로컬 데모에서 변경된 사용자 동선과 휴대폰 폭의 배치를 확인합니다. |
| 배포 절차 변경·릴리스 점검 | `ecc:deployment-patterns`로 `docs/deploy.md`의 백업·상태 확인·실패 시 복구 절차를 점검합니다. |
| 문서 정합성·인수인계 체계 점검 | `ecc:docs-governance`로 제품 규칙, 운영 절차, 인계 문서의 책임과 참조를 확인합니다. 단순 문구 수정은 해당 문구와 diff를 확인하면 됩니다. |

기능 작업은 표의 `orch-*` 스킬 하나로 시작합니다. 스킬이 공유하는 `orch-pipeline`이 작업 규모에 맞게 조사·계획·테스트·검토 단계를 정합니다. 계획 승인이 필요한 단계에서는 사용자에게 계획을 제시합니다. 예를 들어 점수 계산 오류라면 오류 수정 절차를 따르고, 누적 순위까지 영향을 받으면 영향 분석을 더합니다.

## 새 기능의 설계 협의

1. 조율자는 `ecc:dev-team`을 적용해 제품(PM), 설계, 개발, 품질(QA) 역할을 독립된 하위 에이전트에 맡깁니다. 각자 같은 요청과 확정 규칙을 읽고 사용자 가치와 범위, 기존 구조에 미치는 영향, 최소 구현, 완료를 입증할 테스트를 각각 제안합니다. 동시 실행 한도에 닿으면 나머지 역할을 다음 차례에 실행합니다.
2. 조율자는 제안을 모아 일치하는 점과 충돌하는 점을 확인합니다. 충돌하면 해당 역할에 상대방의 근거를 전달해 재검토한 뒤 합의안과 남은 쟁점을 정리합니다. 예컨대 기존 기록에 새 규칙을 소급할지처럼 선택의 영향이 크고 판단이 갈리면 `ecc:council`로 선택지를 비교합니다. 제품 정책을 바꾸는 결정은 근거와 함께 사용자에게 제시합니다.
3. 조율자는 합의된 범위, 완료 조건, 수정할 경로와 검증 방법을 구현 계획으로 정리합니다. 설계 논의만 요청받았다면 설계안과 쟁점을 전달하고 마칩니다.

## 구현 위임과 완료 확인

- 앱 코드와 테스트 편집은 조율자가 Codex 구현 하위 에이전트에 위임합니다. 요청에 계획, 허용 파일, 적용할 ECC 스킬, 완료 조건을 적습니다. 같은 파일의 편집은 한 작업자에게 맡깁니다. 설명이나 단순 문서 수정은 현재 세션에서 마칠 수 있습니다.
- 구현자는 `orch-pipeline`의 TDD 단계에 따라 동작 하나씩 진행합니다. 새 기능·동작 변경·버그 수정에서는 기대 동작을 테스트로 적고 의도한 이유로 실패하는지 확인합니다(RED). 최소한의 구현으로 같은 테스트를 통과시킨 뒤(GREEN), 필요한 코드 정리를 하고 다시 실행합니다(REFACTOR). 기존 동작을 유지하는 리팩터링은 변경 전 통과하는 테스트로 시작합니다. 구현자는 실행 명령과 단계별 결과를 회신합니다.
- 구현에 참여하지 않은 검토 하위 에이전트가 diff를 완료 조건과 대조하고 관련 검사를 직접 실행합니다. 특히 점수·권한·보안·저장 데이터·배포 변경은 해당 경계 조건을 확인합니다. 검토자는 발견 사항과 근거를 회신하고, 구현자가 수정하면 해소됐는지 다시 확인합니다.
- 앱 변경의 기본 검증은 `python3 -m unittest discover -s tests -v`입니다. `web/app.js` 변경 시 `node --check web/app.js`도 실행합니다. 문서만 바뀌면 참조와 `git diff --check`를 확인합니다.
- 사용자에게 변경 결과, 실행한 검사, 미확인 사항을 보고합니다. 다음 대화에 필요한 상태나 결정이 바뀌면 `HANDOFF.md`를 갱신합니다.
- 커밋과 공개 배포는 각각 사용자 요청이 있을 때 진행합니다. `v*` 태그 푸시와 수동 배포 워크플로 실행도 공개 배포에 포함됩니다.
